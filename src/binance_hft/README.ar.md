# مشروع إيجاليس - الطبقة الأولى
## نظام التداول عالي التردد لعقود Binance المستقبلية

### 🏛️ الوثيقة المرجعية الرسمية: الطبقة الأولى (مشروع إيجاليس - الطبقة الأولى)
**التصنيف:** سري / هندسة أنظمة عالية التردد (HFT)
**البيئة المستهدفة:** عقود Binance المستقبلية (Rust / Tokio Async Runtime)

---

## 🔧 الفلسفة المعمارية

تخضع هذه الطبقة لثلاثة مبادئ أساسية:

### 1. الحتمية الزمنية
يجب أن يكون وقت معالجة أي حزمة بيانات ثابتاً تقريباً (مستوى الميكروثانية). لا مكان للعمليات التي تسبب تأخيرات مفاجئة (Jitter).

### 2. انعدام الثقة في الشبكة
نفترض أن الاتصال سينقطع، وأن الحزم ستُفقد، وأن خوادم Binance ستعاني من ازدحام. النظام مصمم لاكتشاف ذلك ذاتياً والتصحيح دون تدخل بشري.

### 3. صفر تخصيص ديناميكي
في حلقة المعالجة الحرجة (Hot Path)، يُمنع منعاً باتاً طلب ذاكرة جديدة (Heap Allocation). كل الهياكل يجب أن تكون مخصصة مسبقاً (Pre-allocated) عند بدء التشغيل.

---

## 📦 حزمة التقنيات والمكتبات المعتمدة

تم اختيار هذه المكتبات بناءً على مقاييس الأداء (Benchmarks) وتجنبها لـ "Garbage Collection":

- **إدارة العمليات غير المتزامنة:** Tokio (مع إعداد multi_thread و worker_threads مساوٍ لعدد أنوية المعالج الفيزيائية)
- **اتصالات WebSocket:** tokio-tungstenite مع rustls لتشفير TLS فائق السرعة
- **تحليل البيانات (Parsing):** simd-json (يستخدم تعليمات وحدة المعالجة المركزية SIMD لتحليل JSON أسرع بـ 3 مرات من serde_json التقليدي)
- **هياكل البيانات المتزامنة:** crossbeam (لقنوات الاتصال الخالية من الأقفال Lock-free channels) و rtrb (Real-Time Ring Buffer لنقل البيانات بين الـ Threads)
- **إدارة الذاكرة:** object-pool لإعادة تدوير الكائنات وتجنب عمليات الحذف والإنشاء

## 🧩 المكونات الأساسية للطبقة

### 3.1. محرك النقل والاتصال (Network & Transport Engine)
مسؤول عن الحفاظ على اتصال حي ومستمر مع تدفقات Binance.

**الاشتراكات المطلوبة (Per Symbol):**
- `<symbol>@depth@0ms` (تحديثات دفتر الأوامر التفاضلية اللحظية)
- `<symbol>@aggTrade` (تدفق الصفقات المنفذة)
- `<symbol>@markPrice@1s` (سعر التحديد لتجنب التصفية ومراقبة Funding)
- `<symbol>@forceOrder` (أوامر التصفية الإجبارية - مؤشر على تحركات الحيتان)

**التصميم الهندسي:** يتم تخصيص Thread منفصل (OS Thread) لكل اتصال WebSocket لضمان عدم تداخل معالجة البيانات مع شبكة الإدخال/الإخراج (I/O).

### 3.2. محرك التحليل فائق السرعة (Ultra-Fast Deserialization Engine)
**الوظيفة:** تحويل تدفقات JSON النصية إلى هياكل بيانات Rust ثنائية (Binary Structs) بأقل تكلفة ممكنة.

**التحصين ضد الفشل (Zero-Copy Parsing):** بدلاً من إنشاء String جديدة لكل سعر أو كمية، يقوم simd-json بقراءة البيانات مباشرة من مخزن الشبكة (Network Buffer) كـ &str (مراجع). هذا يقلل استهلاك الذاكرة والـ CPU بنسبة تصل إلى 70%.

### 3.3. مدير دفتر الأوامر المحلي (Local Order Book - LOB Manager)
هذا هو القلب النابض. يجب أن يكون LOB مطابقاً تماماً لدفتر Binance في الوقت الفعلي.

**هيكل البيانات (Data Structure):**
- لا نستخدم HashMap لأنه غير مرتب
- لا نستخدم BTreeMap التقليدي لأنه بطيء في التحديثات المكثفة
- **الحل الهندسي:** استخدام Dual-Array مع فهرسة ثنائية (Binary Indexed Tree) أو Skip-List مخصص. نحتفظ بمصفوفتين ثابتتي الحجم (Pre-allocated Arrays): واحدة لأوامر الشراء (Bids) مرتبة تنازلياً، وأخرى لأوامر البيع (Asks) مرتبة تصاعدياً. يتم تحديث الكميات (Quantities) عبر الفهرس المباشر (O(1) complexity).

**بروتوكول المزامنة الصارم (The Sync Protocol):**
1. **اللقطة الأولية (Snapshot):** جلب حالة الدفتر عبر REST API (GET /fapi/v1/depth?limit=1000)
2. **تخزين التحديثات (Buffering):** أثناء جلب اللقطة، يتم تخزين تحديثات WebSocket في Ring Buffer مؤقت
3. **الدمج والتحقق (Merge & Validate):** تطبيق التحديثات المخزنة على اللقطة. يجب أن يكون lastUpdateId في اللقطة مساوياً أو أقل من u (Update ID) في أول رسالة WebSocket
4. **التحقق المستمر (Continuous Checksum):** كل رسالة WebSocket تحتوي على U (First Update ID) و u (Last Update ID) و pu (Previous Update ID). القاعدة الحتمية: يجب أن يكون pu للرسالة الحالية مساوياً لـ u للرسالة السابقة

### 3.4. ناقل الأحداث الداخلي (Internal Event Bus)
**الوظيفة:** نقل البيانات من LOB إلى "محرك توليد الإشارات" (Layer 2).

**التصميم الهندسي:** استخدام rtrb (Ring Buffer) أحادي المنتج/أحادي المستهلك (SPSC). هذا يمنع أي استخدام للأقفال (Mutexes) التي تسبب توقف الـ Thread (Thread Contention).

## ⚠️ التحليل المقارن للفشل والنجاح

نطبق "العدسة المزدوجة" على كل نقطة حرجة في الطبقة الأولى:

### ⚠️ سيناريو الفشل الأول: انقطاع WebSocket الصامت (Silent Disconnect)
**المشكلة:** قد ينقطع الاتصال دون أن يرسل الخادم إشارة Close. البوت سيستمر في التداول بناءً على دفتر أوامر "ميت" (Stale Data)، مما يؤدي إلى دخول صفقات بأسعار خاطئة وخسائر فادحة.

**التحصين الجذري (Circuit Breaker):**
- تطبيق مؤقت نبضات القلب (Heartbeat Watchdog). إذا لم يتم استلام أي رسالة pong أو بيانات سوقية خلال 2000 مللي ثانية، يتم اعتبار الاتصال ميتاً
- يتم إطلاق حدث MarketDataHalt فوري
- يقوم البوت بإلغاء جميع الأوامر المفتوحة (Cancel All Open Orders) عبر REST API كإجراء وقائي، ثم يبدأ بروتوكول إعادة الاتصال الأسي (Exponential Backoff Reconnection)

### ⚠️ سيناريو الفشل الثاني: فقدان حزمة بيانات (Packet Loss / Sequence Gap)
**المشكلة:** ازدحام الشبكة يؤدي إلى ضياع رسالة WebSocket. إذا كان pu != u السابق، فإن دفتر الأوامر المحلي أصبح تالفاً (Corrupted). التداول الآن هو مقامرة عمياء.

**التحصين الجذري (State Recovery):**
- عند اكتشاف فجوة في التسلسل (Sequence Gap)، يتوقف المحرك فوراً عن إرسال إشارات التداول
- يتم مسح الـ LOB المحلي بالكامل
- يتم إرسال طلب Snapshot جديد عبر REST API
- أثناء انتظار الـ Snapshot، يتم تجاهل أوامر التنفيذ الجديدة (Trading Suspended) لحماية رأس المال

### ⚠️ سيناريو الفشل الثالث: طوفان البيانات (Data Flood & Memory Exhaustion)
**المشكلة:** أثناء تقلبات السوق العنيفة (Flash Crashes)، ترسل Binance آلاف التحديثات في الثانية. إذا كان "محرك الاستراتيجية" أبطأ من "محرك البيانات"، ستمتلئ قنوات الاتصال (Channels)، مما يؤدي إلى استنفاد الذاكرة (OOM Crash) أو التداول ببيانات متأخرة ثوانٍ (Latency Spike).

**التحصين الجذري (Backpressure & Drop Strategy):**
- استخدام قنوات ذات سعة محدودة (Bounded Channels) بحجم مثلاً 10,000 رسالة
- استراتيجية "الأحدث هو الأهم" (Drop-Oldest): إذا امتلأت القناة، يقوم محرك البيانات بحذف أقدم رسالة غير معالجة واستبدالها بالرسالة الجديدة. في الـ Hyper-Scalping، البيانات التي عمرها 50 مللي ثانية تعتبر تاريخاً قديماً ولا قيمة لها. من الأفضل اتخاذ قرار بناءً على أحدث سعر، بدلاً من الانتظار لمعالجة أسعار ميتة

### ⚠️ سيناريو الفشل الرابع: تجاوز حدود معدل الـ API (REST API Rate Limits)
**المشكلة:** عند حدوث انقطاعات متكررة، قد يحاول البوت جلب الـ Snapshot مئات المرات، مما يؤدي إلى حظر عنوان الـ IP من قبل Binance (HTTP 429 / 418 Ban).

**التحصين الجذري (Rate Limit Shield):**
- تطبيق محدد معدل محلي (Local Token Bucket) يمنع إرسال أكثر من طلب Snapshot واحد كل 3 ثوانٍ لكل رمز تداول
- استخدام مفاتيح API متعددة (Multi-API Key Routing) مخصصة للبيانات العامة (Public Data Only) لتوزيع الحمل وتجنب حظر المفتاح الرئيسي المسؤول عن التنفيذ

## 💡 استراتيجية تحسين الذاكرة والمعالج

لضمان تحقيق كمون شبه صفري (Zero-Latency):

### تثبيت الـ Threads (Thread Pinning)
استخدام مكتبة core_affinity لتثبيت Thread الخاص بـ LOB على نواة معالج محددة (CPU Core 1)، ومنع نظام التشغيل من نقله (Context Switching)

### تجنب الـ Heap Allocation
جميع هياكل الرسائل (Message Structs) يتم إنشاؤها على المكدس (Stack)

### تجميع البيانات (Cache Locality)
تصميم هيكل بيانات LOB بحيث تكون الأسعار والكميات متجاورة في الذاكرة (Array of Structs بدلاً من Struct of Arrays) لضمان الاستفادة القصوى من ذاكرة التخزين المؤقت للمعالج (L1/L2 Cache)
